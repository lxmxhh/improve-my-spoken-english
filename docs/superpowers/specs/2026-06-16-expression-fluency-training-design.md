# Expression & Fluency Training Design

**Date:** 2026-06-16
**Status:** Ready for development planning
**Scope:** 把当前"看着完整参考句朗读"的练习形态，升级为"自己组织语言产出"的训练形态；并建立一套可持续强化、且让用户亲自感知到进步的机制。

## 1. 目标

让产品训练用户在真实交流瞬间"把脑子里的意思，及时、自然地用英语说出口"的能力，并满足三个要求：

1. **真正训练"组织表达"**：用户必须自己产出语言，而不是照着屏幕读。
2. **持续强化**：练习要形成闭环，越练越强，薄弱点被反复打磨。
3. **进步可感知**：用户能亲耳、亲眼确认自己在变好，而不是只看到一个抽象分数。

兼容约束（沿用 Flow Coach 设计原则）：

- 不删除现有字段，不改变现有字段语义，新字段一律可选。
- 现有 `MicButton`、`/api/transcribe`、`/api/evaluate-line`、`/api/pronunciation-assess`、`/api/pronunciation-coach`、Flow Coach、录音回放继续可用。
- 没有新数据时，旧流程必须照常工作。

## 2. 第一性原理

### 2.1 当前产品真正训练的是什么

把"会说英语"拆到不可再分，说话是一条认知流水线，每个环节是独立技能：

```text
听懂对方 → 想清楚要表达什么 → 把意思编码成英文 → 发出声音 → 边说边监控修正
（理解）   （概念，与语言无关）   （组织：检索+造句）   （发音）   （自我纠错）
全程：实时压力 + 互动
```

对照当前实现：

| 环节 | 当前是否训练 |
|---|---|
| 听懂对方 | 弱 |
| 想清楚要说什么 | 完全跳过（答案直接给了） |
| **组织成英文（B1–B2 的真正瓶颈）** | **完全跳过（全程 `You can say: {完整句}`，照读即可）** |
| 发音 | 训练得很好（Azure 四维 + 单词级 + Flow Coach） |
| 监控修正 | 中（AI Coach 反馈，但只在发音轴） |

**结论：当前产品训练的是"朗读 + 跟读纠音（shadowing）"，被命名成了"对话练习"。它把最容易测量的发音做到很强，却完整跳过了真正的瓶颈——组织表达。**

### 2.2 组织表达能力的本质

组织表达不是"知不知道"，而是"调得出、调得快"。机制上是上面那条链的**自动化程度**：从费力的受控加工，变成自动加工，并大量使用**预制块（chunks）**绕过实时造句。

因此可训练、可衡量的维度是流利度三维 + 复杂度（SLA 的 CAF 模型）：

- **速度流利**：语速、起说延迟。
- **断点流利**：停顿频率/时长、填充词（um/uh）。
- **修复流利**：重启、自我纠正、重复。
- **复杂度**：句长、从句、用词丰富度。

铁律：**这些维度互相拉扯（CAF trade-off）**——逼复杂度会牺牲流利度。所以严禁用单一总分，否则用户会用"又快又简单的废话"刷分。

### 2.3 核心设计原则

> **当前产品提供恒定、最大化的脚手架；学习的本质要求脚手架随能力逐步撤掉（scaffolding fading）。**

把完整答案永远摆在眼前，等于把脚手架焊死。产品的核心机制，应是一把可滑动的尺子——根据用户水平和表现，决定露出多少支撑，并把用户从"照读"推向"自由产出"。

## 3. 脚手架阶梯（Scaffolding Ladder）

每个 user turn 的支撑量分级。产品的核心任务是把用户从 L0 往上推，卡住时退一格。

```text
L0  完整句子 → 照读                         （当前产品 = 永远停在这里）
L1  先看句子 → 句子消失 → 凭记忆说            （加入检索）
L2  只给关键词 / 骨架 → 自己补全              （加入造句）
L3  只给"要表达的意图"(中文/目标) → 自由说，语义判方向   （真正的组织）
L4  只给"场景" → 开放回答，AI 分支追问        （接近真实对话）
```

设计要点：

- **真正该自适应的轴是这把脚手架尺子，而不是"词汇难度"。** 初学者停在 L0–L1 合理，高手该被推到 L3–L4。
- **支撑可手动召回**：用户卡住时点"给点提示"，逐级降档（意图 → 关键词 → 完整句），系统记录"用了几次提示"。
- **范例后置**：原来的参考句从"事先给的剧本"变成"用户先说、说完才揭晓的范例 + 跟读目标"。同一段文字，前置 vs 后置，性质完全不同。
- **现有发音层接在产出之后**：用户先产出 → 揭晓范例 → Flow Guide + Azure 发音精修 + 跟读。Flow Coach 全部复用，只是位置后移。

## 4. 自由表达的方向评价

L3/L4 没有唯一参考答案，必须解决"如何判断用户答得在不在题上"。

### 4.1 把"评价"拆成两条独立轴

1. **方向轴（拦截）**：是否回答了问题 / 在不在题上。决定能否通过。**必须宽松**。
2. **质量轴（不拦截）**：语法、用词、地道度、发音。只给建议，永不挡路。

训练目标是"让用户敢于、能够把意思组织出来"，所以方向轴只拦三种情况：

- 确实答非所问；
- STT 把对的答案识别成乱码（先怀疑识别错，不惩罚用户）；
- 没说出有效内容（太短/沉默/敷衍）。

### 4.2 最高杠杆：把"可接受答案空间"前置生成

在生成脚本时，为每个教练问题顺便产出三样东西（运行时直接对照，又快又稳）：

```ts
interface CoachPromptAnchor {
  intent: string;          // 言语功能，如 "describe a past routine"
  keyPoints: string[];     // 2–3 个可接受回答方向，如 ["提到起床时间", "提到一项活动"]
  sampleAnswer: string;    // 示范答案，也正好是揭晓时给用户看的范例
}
```

这三样本就是脚手架渐隐所需素材（`sampleAnswer` = 揭晓的参考句），一鱼多吃。

### 4.3 评价方案选型

| 方案 | 做法 | 取舍 | 用途 |
|---|---|---|---|
| LLM 锚定判断（推荐核心） | 对照预生成 `keyPoints` 做宽松二元判方向 | 一致性高、可解释、运行时快 | L3 方向门 |
| LLM 结构化 rubric | 在相关性/完整性/连贯性维度打分 | 反馈可执行 | 质量轴 |
| 言语功能覆盖 | 判断是否完成 `intent` 要求的功能 | 内容无关、更宽松 | 进阶判据 |
| 向量相似度 | 用户回答 vs 示范答案 cosine | 便宜快，但易误判 | 仅粗过滤 |
| 生成式续接（不判对错） | 教练像真人接话，跑题就自然引导 | 最像真实对话、无考试感 | L4 开放对话 |

### 4.4 推荐：分级级联

**L3（给意图、自由产出，要 pass/fail）：**

```text
1. 廉价闸门：非空、长度够、不是乱码（挡掉 STT 失败与敷衍）
2. （可选）embedding 粗过滤：明显离题给软提示，不必调 LLM
3. LLM 锚定判断：对照 keyPoints 宽松判方向
   prompt 要点：只判在不在题，不判语法；不确定时判通过(fail-open)；给 1–2 个 pass/fail 例校准
4. 通过后，质量轴(rubric) + Azure 发音 异步给"怎么说更好"，不拦截
```

**L4（开放对话、分支）：** 用生成式续接，不做硬 pass/fail；评价沉到对话结束后做一次整体小结。

### 4.5 边界

- **fail-open**：判断系统报错或拿不准一律放行（与现有 `/api/evaluate-line` 一致）。
- **STT 误判保护**：把 `sampleAnswer` 作为 prompt 上下文喂给 STT 提高识别，再判方向。
- **太短/沉默**：归为"无有效内容"，不计失败，提示重来（复用 `onNoSpeech`）。

## 5. 训练机制：怎么让它不断加强

### 5.1 训练法（每条对应一个原理）

1. **检索式产出（核心）**：先自己说、说完才揭晓。检索动作本身才长能力（testing effect / output hypothesis）。
2. **脚手架渐隐**：见 §3。
3. **限时复述 4-3-2**：同一内容 60s → 40s → 20s。内容不变、时间递减，强迫提速，把受控加工压成自动加工。练流利度最快见效的技术。
4. **任务复述**：同类任务换内容再做，第二遍更快更顺，天然产生"我进步了"的对比。
5. **块状化训练**：抽出用户卡住处和范例里的高频块反复练，下次整块调用，绕过实时造句。**复用 Flow Coach / 连读层**。
6. **个性化间隔重复——复练"说不出来的结构"，不是单词。**

### 5.2 强化闭环引擎

单次练习只是点，持续变强必须成环。引擎的燃料是**用户自己的失败**：

```text
说不出来 / 卡顿 / 降到更低脚手架失败
  → 捕捉成一个"个人表达项"（某结构 / 某块 / 某场景功能）
  → 几天后在新内容里重现这个项（间隔重复）
  → 用更低脚手架复测
  → 连续 N 次低脚手架成功 → "毕业"
```

与 PRD 改进文档里的"错误本"是同一思路，但升级为**产出能力的错误本**，而非发音/单词的错误本。

```ts
interface ExpressionItem {
  id: string;
  pattern: string;          // 卡住的结构/块/功能描述
  exampleContext: string;   // 首次出现的场景句
  scaffoldLevelFailed: number; // 在哪一档失败
  successStreak: number;    // 连续低脚手架成功次数
  status: "learning" | "mastered";
  nextReviewDate: string;   // 间隔重复调度
}
```

## 6. 衡量与进步感知

### 6.1 能提取的信号

| 信号 | 反映 | 来源 |
|---|---|---|
| 起说延迟（prompt 结束→开口） | 检索速度（卡不卡） | Azure timing |
| 语速（词/分钟） | 速度流利 | timing |
| 停顿 / 填充词 | 断点流利 | 转写 + timing |
| 一口气词数（mean length of run） | 流利度强指标 | timing |
| 自我纠正 / 重启次数 | 修复流利 | 转写模式 |
| 句长 / 从句 / 用词丰富度 | 复杂度 | LLM 打分 |
| 达成的脚手架等级 | 真实能力档位 | 系统已知 |
| 提示依赖度（用了几次提示） | 独立产出能力 | 系统已知 |

> 注：起说延迟、语速、停顿、一口气词数依赖 word-level timing，对应 Flow Coach 设计的 Phase 2（Azure detailed result 的 `offsetMs` / `durationMs`）。在拿到 timing 前，先用"脚手架等级 + 提示依赖度 + 新旧录音对比"驱动感知。

```ts
interface FluencyMetrics {
  startDelayMs?: number;
  wordsPerMinute?: number;
  pauseCount?: number;
  fillerCount?: number;
  meanLengthOfRun?: number;
  selfRepairCount?: number;
  complexityScore?: number;   // LLM 0–100
  scaffoldLevel: number;      // 0–4，本轮达成档位
  hintsUsed: number;
}
```

`Session` 扩展（向后兼容，全部可选）：

```ts
interface Session {
  // ...existing fields...
  avgScaffoldLevel?: number;
  avgStartDelayMs?: number;
  avgWordsPerMinute?: number;
  expressionItemsMastered?: number;
}
```

### 6.2 让用户"感受得到"——对比与叙事，而非裸数字

按打动力排序：

1. **脚手架依赖度下降（主进度指标）**："两周前这个场景你要看完整句，现在只看一个关键词就能答。" 最贴近真实能力、最难刷、最有升级感。做成产品主进度条。
2. **新旧录音并排听（杀手锏）**：同类问题，放出一个月前与今天的录音对比。**听到自己变流利，胜过任何分数。** app 已在存录音，现成资产直接复用。
3. **起说延迟下降**："以前愣 6 秒才开口，现在 2 秒。" 直击"卡住/冷场"这个最痛的点。
4. **4-3-2 当场变快**：同一段第 1 遍 18s、第 3 遍 11s，单次练习内即给即时胜利。
5. **一口气说完**：从断三次到一句话连贯，可视化展示。

### 6.3 两个设计纪律

- **绝不用单一总分**（CAF 互相拉扯，合成分会被"又快又简单"刷穿）。展示 2–3 条轴 + 趋势，叙事主线锁定"需要的支撑更少了"。
- **用里程碑而非纯数字**："你已升级到 Daily Life 的'关键词模式'。" 把进步做成可解锁的等级事件。

## 7. 分阶段排期

### Phase 1：先产出，后揭晓（最小切口，验证核心假设）

不依赖 timing，只改 session 的呈现顺序：

1. 脚本生成时附带 `CoachPromptAnchor`（intent / keyPoints / sampleAnswer），无 AI key 时规则兜底。
2. user turn 默认隐藏完整参考句，只显示教练问题 + 一行意图/关键词。
3. 用户先说 → `/api/evaluate-line` 升级为"锚定式宽松判方向"。
4. 说完才揭晓 `sampleAnswer` + 现有 Flow Guide + Azure 发音 + 跟读。
5. "给点提示"按钮逐级降档，记录 `hintsUsed` 与达成的 `scaffoldLevel`。

验收：

- assessment/practice 都能"先自己说，再看范例"。
- 跑题/乱码被宽松拦截，对的答案不被冤枉，系统出错时 fail-open。
- session 记录 `scaffoldLevel` 与 `hintsUsed`。

### Phase 2：限时复述 + 当场变快

1. 在一个 turn 内提供 4-3-2 复述（同内容、递减时限）。
2. 展示同段三遍的用时/起说延迟对比（即时胜利）。
3. 新旧录音并排回放（复用已存录音）。

验收：单次练习内用户能看到自己第 3 遍比第 1 遍快；能并排听到新旧录音差异。

### Phase 3：强化闭环 + 进步趋势

1. 失败/卡顿捕捉为 `ExpressionItem`，间隔重复调度。
2. 在新场景重现待复练项，低脚手架复测，连续成功则毕业。
3. history 增加进步趋势：脚手架等级、起说延迟、已掌握表达项数。
4. 引入 word-level timing（承接 Flow Coach Phase 2），补齐 `FluencyMetrics` 中依赖 timing 的字段。

验收：薄弱点会被重现复练；history 能看到"支撑变少 / 起说变快 / 掌握项增加"的趋势。

## 8. 测试计划

### 8.1 单元测试

- `CoachPromptAnchor` 生成与规则兜底。
- 锚定式方向判断：在题/跑题/乱码/太短四类样例。
- fail-open 行为。
- 脚手架降档与 `hintsUsed` 计数。
- `FluencyMetrics` 计算（起说延迟、语速、停顿、一口气词数）。
- `ExpressionItem` 间隔重复调度与毕业逻辑。

### 8.2 API 测试

- 脚本生成返回结构化 anchor；无 AI key 时返回兜底 anchor。
- `/api/evaluate-line` 无 anchor 时保持旧的宽松语义行为。
- `/api/evaluate-line` 有 anchor 时方向判断稳定且偏宽松。

### 8.3 手动验收样例

用以下问题验收"先产出后揭晓 + 方向判断"：

```text
What did you do this morning?
Why do you want to learn English?
Can you describe your hometown?
What would you do if you missed your train?
```

每题至少验证：

- 隐藏参考句下用户能自己产出。
- 合理但措辞不同的回答判通过；明显跑题判不过且引导。
- 揭晓范例后跟读/发音精修可用。
- 同段 4-3-2 第 3 遍更快。

### 8.4 回归

每次改动至少运行：

```bash
npm run build
```

涉及 lint/type 敏感文件时，运行项目已有 lint / typecheck。

## 9. 风险与约束

### 9.1 自由表达会增加挫败感

隐藏答案让用户一开始更难。缓解：保留"给点提示"逐级降档；方向轴宽松、fail-open；范例总在尝试后揭晓，永不卡死。

### 9.2 LLM 判方向的一致性

缓解：用 `keyPoints` 锚定 + 明确"只判方向不判语法" + 给校准样例 + 不确定判通过；用人工标注集定期回归校准。

### 9.3 timing 数据当前缺失

起说延迟、语速等依赖 Azure word timing，当前未暴露。缓解：Phase 1/2 先用"脚手架等级 + 提示依赖度 + 新旧录音对比"驱动感知，timing 字段在 Phase 3 接入（承接 Flow Coach Phase 2），全部可选。

### 9.4 单一分数被 gaming

缓解：不做合成总分；多轴展示 + 趋势 + 里程碑；复杂度与流利度并列呈现以暴露 trade-off。

### 9.5 STT 误判惩罚正确答案

缓解：方向判 fail 时先怀疑识别错误；把 `sampleAnswer` 作为 STT 上下文；太短/沉默不计失败。

---

## 10. 决策结论

- 产品核心从"训练发音"升级为"训练发音 + 组织表达"，后者是 B1–B2 的真正瓶颈。
- 机制核心是**脚手架渐隐**：先产出、后揭晓、再精修，支撑随能力撤除。
- 自由表达用**预生成锚点 + 宽松 LLM 判方向**，质量反馈走独立非拦截轴；L4 改为生成式对话。
- 强化靠**以用户失败为燃料的间隔复练闭环**；进步感知靠**脚手架依赖度↓ + 起说延迟↓ + 新旧录音并排听**，而非裸分数。
- 现有资产（录音、`evaluate-line`、Azure/Flow Coach、script-pool、history）几乎全部复用，缺的是呈现顺序与训练闭环，而非新技术。
- Phase 1（先产出后揭晓）是验证核心假设的最小切口，优先落地。

## 11. 实现补充（2026-06-17，落地后的调整）

### 11.1 练习模式反馈改为"评学习者自己说的句子"

问题：Phase 1 把 pass/fail 改成了锚定判方向，但**反馈层（AI Coach + Flow Coach）仍锚定模型答案**，体感像"拿标准答案给我打分"。

调整：
- `/api/pronunciation-coach` 新增 `mode: "free"` 分支：传入 `transcript / question / modelAnswer`，**点评学习者实际说的那句**（语义是否到位 + 语法/用词/自然度小改进），模型答案仅作 AI 内部参考、不要求照说。
- session 练习路径改调 `fetchFreeCoachFeedback`；模型答案那句的连读 `FlowGuide` 在练习模式**不再显示**（它本是 assessment 朗读用的），参考句标签改为"A natural way to say it:"。

### 11.2 自由产出与脚本走向脱节 → 独立提问式脚本

问题：预生成脚本的教练后续台词若"反应"了模型答案的具体内容，学习者自由发挥后对话会脱轨。

决策：采用方向 1（最小改动）。`generate-script` 生成 prompt 约束**每句教练台词为能独立成立的同主题问题**，不复述/不依赖上一句的具体内容（中性过渡词可保留）。保留预生成与零额外延迟。L4 动态生成教练回应留作后续大功能。

### 11.3 已知项（按决策保持现状）

- `BUILTIN_SCRIPTS` / `FALLBACK_SCRIPTS`（约 16 个内置脚本）仍是旧的"反应式"台词，未按 §11.2 改写。影响面：无 AI key 的兜底，以及每次进 session 第一瞬间的占位脚本（很快被缓存的生成脚本替换）。**经确认保持现状**，有 AI 时主路径已符合新约定。
